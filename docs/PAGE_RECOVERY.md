# Page history and recoverable trash (dev)

Ordinary document pages now keep pre-change revisions in the local SQLite database. Open **Page history**, select a saved version and preview its text before choosing **Restore this revision**. Download saved blocks for the complete editor payload; the preview does not render rich media. Historical content is never mounted in an editable autosaving editor.

Restoring requires the page version captured when history was opened. A concurrent edit returns a conflict and leaves both the newer writing and historical snapshot intact. Close history and reload the page before reconsidering the restore. A successful restore creates a new monotonically increasing page version, keeping the replaced writing in history so the restore can itself be reversed. Current parent/project/workspace and linked database/view identifiers are retained. Title, body, icon and cover come from the chosen revision.

**Move to trash** first saves local writing, then performs a version-checked deletion. Use **Page trash** in navigation to restore the same page ID, metadata and writing with a newer version. A stale pre-deletion editor cannot overwrite the recovered page. Pages with active children must be moved/deleted leaf-first and recovered parent-first. The original parent must exist before restoration. Existing databases or records, including their trashed entries, own their backing pages; use database trash rather than deleting those pages separately. History for database-owned pages restores writing, icon and cover while keeping the current title and typed properties under their database owner. This avoids desynchronizing record/database titles or replaying stale typed values.

Revisions and page trash are retained without automatic expiry; no permanent erase or automatic pruning is implemented. History is captured from this upgrade onward, not retroactively. Content/metadata changes made through other page-writing paths are captured by SQLite triggers inside their transaction. A snapshot insertion failure fails the corresponding change. Migration 11 verifies recovery tables and trigger definitions at startup and during archive validation. Older binaries must reject this schema instead of modifying it. The existing complete workspace archive includes these tables, so history and trash migrate with the database. Copy a verified archive before upgrading; V0.0.1 cannot open an upgraded workspace.

History uses stable ID cursors with 100 metadata rows per request; full snapshots load only when selected. Page trash currently shows the latest 250 items; all older entries remain in SQLite and the full workspace archive. There is no guarantee against device loss or disk corruption without a separate verified backup.

Automated acceptance uses disposable synthetic data: version conflicts, restoring/undoing a restore, transaction rollback when revision/tombstone writes fail, ownership and parent ordering, repeated restart, historical ID reservation, bounded history pagination, browser preview/retry/focus/narrow reduced-motion layout, and native portable archive/CLI recovery with revisions and deleted pages. Real historical v6/v7 samples and manual assistive-technology/platform acceptance remain separate open gates in DEVELOPMENT_PLAN.md.
